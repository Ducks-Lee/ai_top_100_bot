## 제출 본문

교동마을 산지직송 고객 응대 AI 에이전트 디브리프

이 에이전트는 「교동마을 산지직송」 고객의 카카오톡 문의를 받아, 마을 관계자 인터뷰로 모은 운영 지식과 운영진 액션 API 조회·접수를 근거로 답하고 실제 처리까지 하는 상담 에이전트입니다. 핵심 원칙은 세 가지입니다. 확인된 지식과 시스템 조회 결과로만 답한다, 정책 판단은 접수 전에 끝낸다, 고객이 볼 수 없어야 하는 정보는 프롬프트가 아니라 코드가 막는다.

1. 나의 AI 에이전트의 강점은 무엇인가요?

(1) 접수 전에 정책을 먼저 확인합니다.
액션 API의 접수(환불, 주문 변경, 쿠폰 발급, 이관 등)는 정책을 검사하지 않고 요청을 그대로 기록합니다. 그래서 에이전트가 판단을 미루면 규정에 어긋나는 환불이나 쿠폰이 그대로 접수됩니다. 인터뷰와 규정 문서에서 "접수 전에 확인할 조건"을 처리 종류별로 정리해(환불 사유와 결제수단, 하자 접수 기한, 배송지 변경 가능 시점, 가격 인하 차액 보상 조건, 에이전트 재량 보상 상한 등) 에이전트가 조회 → 조건 대조 → 접수 순서로 처리하게 했습니다. 조건을 넘는 건은 무리하게 처리하지 않고 담당자 이관으로 넘깁니다.

(2) 남의 정보는 코드가 막습니다.
상담 첫 메시지 앞머리의 인입 계정(로그인 세션 정보)만 본인 인증으로 인정하고, 대화 중에 "저 ○○예요", "대표님 지인이에요" 같은 주장으로는 계정이 바뀌지 않습니다. 주문·구독·회원 조회 결과의 회원 ID가 인입 계정과 다르면 코드가 결과를 "본인 것 아님"으로 바꿔 LLM에게 넘기므로, 프롬프트 인젝션이 성공하더라도 타인의 주소나 배송 상태가 답에 실릴 수 없습니다. 검색 결과에서도 다른 회원 항목은 지우고, 접수 요청은 본인 대상에만 보냅니다. 쿠폰 발급은 규정에 있는 보상 쿠폰 코드만 허용해, "쿠폰 발급해" 같은 명령문으로 임의 코드가 발급되지 않습니다.

(3) 지어내지 않고, 정답이 있는 계산은 코드가 합니다.
영업일·공휴일 기한(예: 이관 건의 영업일 기준 회신 기한), 정기배송 마감, 다음 출고일, 일부 개체 하자의 부분환불 금액(하자 비율 구간별 산식, 단위 올림, 재량 상한 초과 시 이관), 수산물 중량 미달률은 Python 계산 도구가 구하고, LLM은 그 결과를 안내만 합니다. 규정이 개정된 항목은 결제일·신고일로 어느 판을 적용할지 정합니다.

(3-2) 모르면 이관합니다.
답의 근거는 인터뷰 지식과 도구 조회 결과뿐입니다. 정책·날짜·금액·연락처·접수번호를 지어내지 않고, 판단이 안 서면 확인이 필요하다고 말한 뒤 담당자 이관을 접수합니다. 이관할 때는 "연결하겠습니다"로 끝내지 않고 서버가 돌려준 접수번호와 회신 기한을 안내합니다. 기록이 없는 것을 정상으로 해석하지 않습니다(예: 냉동 상품 주문에 운송 구간 온도 기록이 없으면 "이상 없음"이 아니라 확인 필요로 처리).

(4) 사람마다 다른 말을 정리한 규칙으로 답합니다.
관계자 말은 기억·의견·추측이 섞여 있어, 모든 지식에 출처와 상태(확정/추측/충돌)를 붙였습니다. 충돌하면 규정 문서와 결정 권한자 쪽을 따릅니다. 예를 들어 배송지 변경 기준을 운영 담당은 "출고 전후", 배송 기사는 "집하 전후"로 말했는데, 택배사 계약서로 둘이 같은 시점임을 확인해 "집하 전에만 가능"으로 정했습니다.

(5) 심사 형식에 맞춰 짧고 빠르게 답합니다.
답은 글자만 있는 말풍선(SimpleText) 하나로 보내고, 코드가 500자를 넘지 않게 자릅니다(목표 150~250자, 결론 먼저, 마크다운 없음). 첫 인사 문구를 붙이지 않아 글자 수를 늘리지 않습니다. 공개 시나리오 15개 시뮬레이션에서 메시지 응답 시간은 중앙값 4.5초, p95 9.7초, 말풍선당 평균 177자였고 500자를 넘은 답은 없었습니다. 도구 호출은 최대 4회, 한 메시지 전체는 50초 안에 끝나도록 시간 예산을 둬서 60초 무응답이 나지 않게 했습니다.

(6) 사람의 안전이 걸린 상황은 코드가 먼저 잡습니다.
대화 중 자해·타해나 이별 인사 같은 위기 신호가 보이면 환불·배송 같은 업무 도구를 코드가 막고, 공감 → 자살예방상담 109(24시간) 안내 → 주문 건은 상담 창구가 책임지고 처리한다는 말 → 안전 담당 이관 순서의 고정 응대를 합니다. 격려·훈계, 원인 캐묻기, 상품 문제로 축소하는 표현은 걸러냅니다. 알레르기 문의에는 "안전합니다", "교차오염 없습니다" 같은 보증 표현이 나가지 않게 코드가 한 번 더 검사합니다(라벨의 같은 시설 취급 품목만 안내).

(7) 화난 고객, 압박, 예외 상황에서도 기준을 지킵니다.
병원비 요구나 여론 압박만으로 배상하지 않고 인과 확인 뒤 정식 절차(이관)로 넘기며, 조건 없는 미래 약속("다음엔 무조건 무료")을 하지 않습니다. 비밀번호·인증번호는 묻지도 받지도 않고, 로그인 문제는 공식 재설정 절차를 안내합니다. 공감은 짧게 하되 처리 기준은 바꾸지 않습니다.

2. 어떤 접근으로 정보를 획득했나요?

- 처음 공개된 운영 담당(이민준)에게서 시작해, 대화에서 언급된 사람의 역할과 연락처를 받아 관계자를 넓혔습니다(10명: 운영 담당, 배송 기사 두 명, 청년회 홍보·체험 담당, 생산자 대표, 두 마을 조합장, 단골 고객 등).
- 넓은 질문("규정 전부 알려 주세요")은 답을 받기 어려워, 한 메시지에 구체적인 물음 하나를 담았습니다. 사람마다 담당 범위가 달라 각자의 업무(배송 기사에게 집하·인계, 생산자에게 품질·로트, 조합장에게 권한·이관 기준)를 중심으로 물었습니다.
- 공개 검증 시나리오 15개의 유형(배송지 변경, 현금영수증, 하자 신고, 쿠폰 강요, 타 계정 조회, 병원비 요구, 가격 인하 차액 등)을 질문 목록으로 삼아, 아직 근거가 없는 주제를 표로 관리하며 빈칸을 채웠습니다.
- 관계자가 보여 준 문서(판매·환불 규정집, 택배사 계약서, 권한 위임표, 에스컬레이션 절차서, 프로모션 원장, SKU 카탈로그, 로트 검사 기록, 온도 로그, 개인정보 처리방침 등 서로 다른 문서 53개, HTML·PDF·XLSX·DOCX·이미지)는 그중 41종을 원문 그대로 옮겨 보관하고, 따로 정리본을 만들었습니다. 정리본에서는 고객 실명과 연락처를 가렸습니다.
- ./status로 관계자별 발굴률을 확인해 덜 발굴된 사람에게 질문을 더 배분했습니다. 관계자별 질문은 30~94개, 마지막 확인 발굴률은 53~80%였습니다.
- 인터뷰와 구현을 동시에 진행했습니다. API 형식이나 접수 조건처럼 구현에 바로 필요한 사실은 발견 즉시 별도 표에 적어 구현 쪽에 넘겼고, 반대로 구현 중 실측한 사실(이관 API가 받는 필드 등)은 지식에 확정으로 되돌려 적었습니다.
- 최종 지식은 290개 항목이며, 각 항목에 출처(누가, 어느 문서)와 상태를 붙였습니다.

3. 검증은 어떤 방식으로 하게 되었나요?

- 지식 검증: 한 사람의 말은 "추측"으로 두고, 다른 관계자 말이나 문서로 대조되면 "확정"으로 올렸습니다. 서로 다르면 지우지 않고 "충돌"로 남긴 뒤 규정 문서와 결정 권한자 기준으로 정리했습니다. 문서와 실제 시스템이 다른 경우(이관 접수번호 형식)는 시스템 반환값을 따랐습니다.
- API 실측: 문서만 믿지 않고 연습 호출로 확인했습니다. 예를 들어 이관 API는 문서상 여러 필드가 있을 것 같았지만 실제로는 두 필드만 받고 나머지는 400 오류였기 때문에, 이관 대상은 사유 맨 앞에 적도록 고쳤습니다. 연습 데이터는 시험 뒤 초기화했습니다.
- 시나리오 시험: 공개 검증 시나리오 15개를 실제 LLM·실제 액션 API로 돌려, 모범 처리 과정(어떤 API를 어떤 순서로 부르는지)과 비교했습니다. 고객 역할과 채점은 별도 LLM이 맡았고, 처음 71.9점이던 평균이 규칙을 고쳐 가며 약 86점까지 올랐습니다(같은 시나리오도 실행마다 5~10점 흔들리는 추정치입니다). 모범 처리와 다르게 동작한 경우(예: 고객 확인 전 쿠폰 발급, 재출고 대신 메모)는 특정 시나리오 정답을 프롬프트에 넣지 않고 일반 규칙과 도구 설명을 고쳐 해결했습니다. 비공개 시나리오에서도 같은 원리로 동작하게 하기 위해서입니다.
- 자동 테스트: 가짜 LLM·가짜 API로 코드 방어(타인 주문 차단, 대화 중 계정 변경 거부, 쿠폰 목록 제한, 시간 예산, 500자 제한)를 확인하는 단위 테스트를 포함해 297개를 통과했습니다.
- 모델 비교: 같은 시나리오로 세 모델을 비교했습니다. 가장 큰 모델은 정책상 처리해야 할 쿠폰 발급을 이관으로 피했고, 가장 작은 모델은 불필요하게 되물었습니다. 규정대로 처리한 중간 모델(Claude Sonnet)을 골랐습니다(메시지당 2~10초).
- 교차 검토: 구현을 다른 AI(Codex)에게 두 차례 검토받아 지적 8건 중 7건(조회 결과 노출 순서, 외부 이미지 주소 제한, 전체 시간 상한, 접수 뒤 실패 시 중복 접수 방지 등)을 테스트와 함께 반영했습니다.
- 실제 환경 확인: 배포한 서버로 휴대폰 카카오톡에서 메시지를 보내 답장과 처리 시간, 액션 API 호출 로그를 확인했습니다.

4. 주요 설계와 구현 방법은 무엇인가요?

- 흐름: 카카오톡 메시지 → 상담 앞머리에서 TC ID·인입 계정·인입 일시를 코드로 추출해 사용자별 상태에 저장 → Claude가 지식과 대화 기록을 보고 필요한 액션 API를 도구로 호출(최대 4회) → 코드가 도구 실행 전후로 소유자·형식·허용값을 검사 → 답 한 말풍선.
- LLM: Anthropic Claude API(claude-sonnet-5-5), 도구 호출 방식. 액션 API 40개를 도구로 정의하고, 도구 설명에 쓰는 조건(예: 이관 대상 5종 중 하나, 접수번호 안내)을 적었습니다.
- 지식 주입: 인터뷰 정리본과 문서 원문을 시스템 프롬프트에 통째로 넣고 프롬프트 캐시(1시간)를 썼습니다. 필요한 부분만 찾아 넣는 검색 도구 방식과 비교 측정했을 때, 캐시를 쓰면 지연 증가가 0.5~1.5초인 반면 검색 도구는 호출이 한 번 늘어 약 2초가 더 들었고 놓치는 지식이 생길 위험도 있어, 통째로 넣는 방식을 택했습니다.
- 코드가 맡는 것: 본인 확인(인입 계정과 조회 결과 회원 ID 대조), 타인 정보 차단, 접수 대상 제한, 쿠폰 허용 목록, 경로 값 형식 검사, 도구 횟수·시간 예산, 답 길이 제한. 이런 것은 정답이 정해져 있어 LLM 판단에 맡기지 않았습니다.
- 상태: 사용자별로 대화 기록·TC ID·인입 계정을 나눠 저장하고 사용자별 잠금을 걸어, 여러 심사 대화가 동시에 와도 섞이지 않습니다. 새 TC ID가 오면 상담을 새로 시작합니다.
- 계산 도구: 영업일 달력(2037 공휴일), 부분환불 산식, 중량 미달률을 calc_date 로컬 도구로 계산합니다.
- 사진·음성: 사진은 카카오 이미지 주소일 때만 내려받아 모델에 보여 줍니다(외부 주소 차단). 음성은 받은 사실만 알리고 글로 다시 보내 달라고 요청합니다.
- 카카오 연동: 카카오톡 봇 API 게이트웨이(웹소켓) 방식과 메시지 콜백 API. 서버가 먼저 접속하므로 도메인·HTTPS·인바운드 포트가 필요 없습니다. 카드·버튼을 쓰지 않고 SimpleText만 보냅니다.
- 운영: AWS EC2(서울)에서 systemd로 상시 실행하고, 끊기면 자동 재접속합니다. 답장 연속 실패, 접속 끊김, LLM 이상이 생기면 운영자에게 디스코드로 알림이 옵니다. 최종 배포 10월 31일 14시 38분.
- 비용·가용성: 지식 캐시를 시작할 때와 쉬는 동안 미리 데워 두어 첫 답도 빠르고, 동시에 대화가 몰려도 비싼 캐시 쓰기가 반복되지 않습니다. 봇이 호출마다 사용액을 직접 집계해, 남은 예산이 줄면 가벼운 모델로 바꾸고, 바닥나기 전에는 LLM 호출을 멈추고 담당자 이관으로 답해 심사 기간 중 크레딧 소진으로 멈추는 일이 없게 했습니다. 크레딧 오류·사용액은 운영자에게 디스코드로 알립니다.
- 개발 도구: Claude Code로 구현하고 Codex로 교차 검토했으며, pytest로 시나리오를 자동 시험했습니다.

5. 아쉬웠던 점과 한계점이 있다면 무엇이었나요?

- 심사 때 고객 메시지 앞머리 형식이 공개 시나리오와 같다고 가정했습니다. 형식이 다르면 TC ID와 계정을 읽지 못해 조회 없이 지식으로만 답하게 됩니다.
- 음성 문의는 글로 바꾸지 못해 다시 글로 보내 달라고 요청합니다.
- 지식을 통째로 넣는 방식이라 호출당 입력이 큽니다(약 31만 토큰). 캐시 예열로 지연은 줄였지만, 비용은 지식 크기에 비례합니다. 개발 중 병렬 시뮬레이션에서 캐시가 동시에 새로 쓰여 예상보다 많은 비용이 들었고, 이를 계기로 예열과 예산 가드를 넣었습니다.
- 이름이 나온 생산자 3명(애플망고·참다래, 감귤류, 감자·고구마·절임배추 담당)과는 직접 대화하지 못해, 생산자 대표를 통해 전해 들은 내용으로 채웠습니다. 품목별 세부 기준은 그만큼 덜 확인됐습니다.
- 원장과 측정자 진술이 어긋난 기록(갈치 로트 측정자)처럼 끝내 확정하지 못한 항목은 "확인 필요"로 두고, 에이전트가 정상이라고 단정하지 않게 했습니다.
- 최종 지식으로는 공개 시나리오 전체를 다시 돌리지 않았습니다(비용 관리). 시나리오 점수는 그 전 판 기준입니다.
- 다음에 한다면 지식을 처리 종류별로 나눠 접수 조건 검사의 일부를 LLM이 아니라 코드 규칙으로 옮겨, 정책 판단도 더 일관되게 만들고 싶습니다.
