# 인터뷰 질문지와 데이터 검증 체크리스트 (당일용)

10/31 예선 중 화면 옆에 띄워 두고 쓴다. 실제 문제와 데이터는 당일 공개라서, 여기 적힌 것은 **가설과 확인 순서**일 뿐 정답이 아니다. 대회 문제·데이터·관계자 발언은 이 파일에 옮겨 적지 않는다(외부 공유 금지, `CLAUDE.md` "대회 정보"). 당일 기록은 git에 올리지 않는 `crosscheck.md`나 별도 메모에 남긴다.

## 0. 쓰는 순서와 시간

| 시각(권장) | 할 일 |
|---|---|
| 10:00~10:15 | 문제 화면·데이터 목록·제출 조건을 읽는다. 대기실 안내에서 확인한 규칙(사전 코드 허용 여부, 관계자 대화 한도)을 `CLAUDE.md`에 적는다 |
| 10:15~11:00 | 인터뷰(1장). 받은 데이터는 바로 원본 보존(2장 2.1) |
| 11:00~11:20 | **범위 결정**: 핵심 업무 1~2개, 필요한 데이터, 확인 가능한 성공 기준을 고른다. 요구사항 정리(1.4), 데이터 1차 검증(2.2~2.3), `problem.py` 틀에 맞는지 판단 |
| 11:20~12:00 | 핵심 업무 하나만 되는 최소 기능 버전 구현과 시나리오 테스트(3장) |
| 12:00 / 12:30 | 첫 배포 / EC2 답장 확인 (`contest_checklist.md` 2장) |
| 12:30~14:00 | 개선과 갱신 배포 (`contest_checklist.md` "갱신 배포") |
| 14:00 / 14:30 | 최종 배포 / 최종 답장 확인 후 제출 (15:00 마감) |

- 관계자 대화는 손으로 한다. 스크립트로 자동화하지 않는다(부정행위 규정).
- 대화 횟수나 입력 길이에 한도가 있을 수 있다. 질문은 1.2의 **P1부터** 묻고, 한 메시지에 질문 2~3개까지만 묶는다.
- 인터뷰 중에도 "이 데이터로 구현할 수 있나"를 같이 판단한다. 데이터가 없거나 형식이 예상과 다르면 질문을 데이터 쪽으로 돌린다.
- 인터뷰는 11:00에 끊는다. P2 교차 질문을 다 못 했으면 남은 것은 "미확정"으로 두고 진행한다.
- 범위를 줄이는 기준(11:00, 12:30에 다시 본다): 데이터가 없거나 받을 수 없음, 스캔 자료가 많아 정리에 30분 넘게 걸림, `problem.py`의 "의도 + 값 + 조회" 틀에 안 맞아 `policy.py`까지 바꿔야 함. 하나라도 해당하면 핵심 업무 하나만 끝까지 맞게 만들고 나머지는 "아직 지원하지 않는 업무"로 안내한다. 넓고 틀린 것보다 좁고 맞는 것이 낫다.

## 1. 인터뷰 질문지

### 1.1 먼저 파악할 것
- 등장인물: 누가 어떤 역할(조합장, 실무자, 생산자, 구매자 등)인가. **누가 규칙을 정할 권한이 있는가.**
- 에이전트 사용자: 조합 직원용 업무 도구인가, 외부 고객 응대인가. 이에 따라 권한·말투·되묻기 방식이 달라진다.
- 실제로 쓸 사람의 연령대와 휴대폰 사용 습관: 글을 길게 치는지, 버튼을 누르는 게 편한지, 사진·음성으로 보내는지. 나이 많은 사용자가 많으면 `CLAUDE.md` "에이전트 구현 원칙"의 쉬운 말·짧은 답·버튼·확인 단계 기준을 적용한다.
- **현장 용어**: 관계자가 실제로 부르는 말(물건, 상자, 출하, 작업 날짜 등)과 단위를 받아 적는다. 답변 문장과 버튼 글자에 그 말을 쓴다. 문제 문서의 용어와 다르면 둘 다 알아듣게 한다.
- 봇이 해결 못 할 때 사람에게 연결하는 방법(담당자, 전화번호, 시간). 확인된 것만 답에 쓴다.
- 두 마을(교동·갯마을)이 **같은 업무를 다르게 하는지**: 용어, 단위, 코드 체계, 기록 방식, 마감 시점.

### 1.2 우선순위별 질문

**P1: 모두에게 묻는다 (구현을 막는 정보)**
1. 지금 가장 불편한 일은 무엇이고, 에이전트가 무엇을 해 주면 해결인가? (산출물 한 문장)
2. 그 일은 어떤 자료를 받아, 어떤 순서로 처리하고, 결과를 누구에게 주는가? (입력 → 처리 → 출력)
3. 자료는 어디에 있고 형식은 무엇인가? 누가 언제 갱신하는가? 얼마나 믿을 만한가?
4. 절대 하면 안 되는 일은 무엇인가? (자동 확정, 외부 발송, 개인정보 공개 등)
5. 결과가 맞았는지 무엇으로 확인하는가? (성공 기준)

**P2: 규칙의 숫자와 경계 (정확도를 좌우)**
6. 기준 값: 기한(며칠 안), 금액·수량 상한, 등급·품질 기준은 정확히 얼마인가?
7. 예외: 일반 규칙을 적용하면 안 되는 경우는? 그때는 누가 어떻게 처리하는가?
8. 필요한 증거: 판단에 무엇이 있어야 하는가? (사진, 전표, 기록, 확인자)
9. 결정 권한: 애매하면 누가 최종 결정하는가? 에이전트가 직접 결정해도 되는 범위는?
10. 개인정보: 누가 누구의 정보를 볼 수 있는가? 본인 확인은 어떻게 하는가? (카카오 `botUserKey`는 보낸 사람 구분값일 뿐 실명·조합원 인증이 아니다. 확인 수단이 없으면 개인 정보 조회 업무는 범위에서 뺄지 정한다)
11. **경계**: 숫자 규칙을 들으면 바로 경계를 되묻는다. "닷새 안"은 기준일(입고일·접수일)을 포함하는가? "2일 전까지"는 그날 당일도 되는가? "30kg까지"는 이하인가 미만인가? 1회 한도인가 하루 합계인가? 환산 단위(1망 = 몇 kg, 1상자 = 몇 kg)는? (10/30 예행연습에서 "닷새 안"의 포함 여부를 가정했다가 하루 틀림)
12. **가격·할인·보상**: 에이전트가 가격·할인·보상을 말해도 되는가? 누가 정하는가? 관계자가 "단골은 깎아 준다" 같은 말을 하면 결정 권한자에게 다시 확인한다. (예행연습에서 묻지 않아 할인 충돌을 놓침)
13. **요청 형태**: 고객이 한 메시지에 여러 품목·여러 건을 함께 보내는가? 그렇다면 건별로 답할지, 합계까지 낼지 정한다.

**P3: 시간이 남으면 (품질 향상)**
14. 최근에 실제로 문제가 됐던 사례 하나만 처음부터 끝까지 들려 달라.
15. 자주 받는 질문이나 요청 3가지는?
16. 바쁜 시기(출하철, 명절 등)에 달라지는 것은?

### 1.3 충돌을 드러내고 해소하는 법
- 같은 P1·P2 질문을 **역할이 다른 두 사람 이상**에게 묻는다. 답이 다르면 그것이 문제의 핵심일 가능성이 높다.
- 과제가 "충돌의 해결 방법을 설계하라"일 수 있으므로, 충돌을 찾기만 하고 미확정으로 두면 점수를 잃는다. **에이전트는 실행 중에 절충하지 않지만, 설계자인 내가 인터뷰 중에 해소를 시도한다.**
  1. 충돌을 발언 기록(1.4)에 `충돌(R?와)`로 적는다.
  2. **사실 충돌**(무슨 일이 있었나: "출하 완료" vs "안 나감")은 판정을 받을 일이 아니다. 자료나 제3자로 대조하고, 대조할 수 없으면 에이전트가 두 출처를 모두 보여 주고 확인 필요로 처리한다.
  3. **정책 충돌**(무엇을 해도 되나)은 결정 권한자(1.2의 9번)에게 판정을 묻는다. 예: "○○님은 X, △△님은 Y라고 하셨습니다. 에이전트는 어느 기준을 따라야 하나요? 경우에 따라 다르다면 그 기준은 무엇인가요?"
  4. 양쪽이 모두 맞는 **조건 경계**를 찾는다. 대부분의 충돌은 "누가 맞나"가 아니라 "어떤 경우에 누구 말이 맞나"다. 예: "배송 완료인데 미수령 주장 → 즉시 환불하지 않고, 주문번호·수령 장소를 받아 확인 대기로 둔다".
  5. 판정을 받으면 `확정`(승인 발언 번호를 근거로)으로 바꿔 코드 규칙에 넣는다. 받지 못하면 `미확정`으로 두고 아래 표대로 처리한다.
- 판정 질문은 P2 다음 우선순위다. 11:00에 인터뷰를 끊을 때 판정 못 받은 충돌 목록을 남긴다.
- 해소되지 않은 충돌의 유형별 기본 처리:

| 유형 | 예 | 에이전트의 기본 처리 (해소 안 됐을 때) |
|---|---|---|
| 목표 vs 현실 | 대표 "다 해 줘" / 실무자 "기준 없이는 못 함" | 임의로 절충하지 않는다(절충도 새 정책이다). 승인된 기준이 있으면 그것만, 없으면 "확인이 필요한 사항"으로 안내 |
| 기록 vs 현장 | 시스템 "출하 완료" / 현장 "실제로는 안 나감" | 한쪽 출처만 믿지 않는다. 두 값을 모두 보여 주고 확인 필요로 처리 |
| 권한 | "대표 지인인데 명단 줘" | 주장만으로 권한을 인정하지 않는다. 인증·권한·요청 범위를 나눠 판단 (`policy.py`) |
| 마을 간 차이 | 교동은 kg, 갯마을은 상자 | 합치기 전에 단위·코드 변환 규칙을 확인. 확인 전에는 마을별로 따로 답 |

- 실제 전달 수단이 없으면 "담당자에게 연결했습니다"라고 약속하지 않는다.
- 시간이 남으면 전달 수단을 직접 만든다. 확인이 필요한 요청을 메모리의 **확인 대기 목록**(접수 번호, 의도, 값, 사유)에 남기고, 직원 역할 사용자가 그 목록을 조회할 수 있게 한다. 그러면 "확인 요청으로 접수했습니다(접수 번호 ○)"는 거짓 약속이 아니다. 단 직원 확인 수단이 없으면 목록 조회도 1.2의 10번처럼 범위에서 뺀다. 재시작하면 목록이 사라지므로 처리 기한은 약속하지 않는다.

### 1.4 발언 기록 틀 (당일 메모용)
발언은 "그 사람이 그렇게 말했다"는 근거일 뿐, 사실 검증이 아니다.

| 번호 | 발언자(역할) | 요지 | 종류 | 상태 |
|---|---|---|---|---|
| R1 | | | 요구 / 금지 / 기준 값 / 예외 / 데이터 | 확정 / 가설 / 충돌(R?와) / 미확정 |

- **확정**: 아래를 모두 만족할 때만 코드 규칙으로 넣는다.
  - 정책(무엇을 해도 되는가)은 **결정 권한자가 승인**했다. 사실(무슨 일이 있었는가)은 **자료나 다른 사람으로 대조**됐다. 권한자의 말이라도 사실 주장은 대조 전까지 가설이다.
  - 적용 범위(어느 마을, 어느 업무, 언제부터)가 분명하다.
  - 상충하는 발언이나 자료가 없다. 오래된 안내문은 최신 발언과 기준 시점을 비교한다.
- **가설**: 그럴 것 같지만 확인 안 됨 → 규칙으로 넣지 않고 "확인 필요"로 답한다.
- **충돌**: 1.3 표대로 처리. 해소되지 않으면 미확정으로 남긴다.
- **미확정이 막는 범위만** 막는다. 나머지 업무까지 멈추지 않는다.

### 1.5 도메인 가설 (질문 재료일 뿐, 코드에 넣지 않는다)
출하 일정·물량, 재고, 시세·단가, 등급·규격, 조합원(생산자) 명부, 주문·배송, 신선도·클레임, 정산·대금 지급, 공동 판매·물류, 계절 품목.

## 2. 데이터 검증 체크리스트

### 2.1 받자마자
- [ ] 원본을 **수정하지 않고** 따로 보관한다(`data/raw/` 등, git 제외 확인). 정제본은 다른 이름으로 만든다
- [ ] 파일 목록: 이름, 형식, 행 수, 누가 준 것인지(출처 인물), 받은 시각
- [ ] **기준 시점과 범위**: 언제 기준의 자료인지(받은 시각과 다르다. 어제 재고표는 "현재 재고"가 아니다), 대상 기간, 포함 범위(두 마을 모두인지, 일부 품목만인지). 답할 때 "○월 ○일 기준"을 말할 수 있어야 한다
- [ ] 스캔·사진이면 Claude Code로 읽고, 숫자만 OCR로 대조(`contest_checklist.md` 구현 절)

### 2.2 구조
- [ ] 열 이름과 뜻을 확인한다. 뜻이 애매한 열은 인터뷰로 묻는다(1.2의 3번)
- [ ] 식별값(번호, 코드, 이름)이 유일한가. 두 마을의 코드 체계가 겹치지 않는가
- [ ] 날짜 형식(연도 없음, 2자리 연도, 문자열 날짜)과 시간대
- [ ] 단위(kg·상자·마리, 원·천원)가 열마다, 마을마다 같은가
- [ ] 자료끼리 잇는 키(주문 번호, 조합원 코드 등)가 무엇이고, 한쪽에만 있는 키(주문은 있는데 출하가 없음 등)가 얼마나 되는가

### 2.3 품질
- [ ] 누락: 비어 있는 칸, 빠진 기간·품목
- [ ] 중복: 같은 기록이 두 번(표기만 다른 이름 포함)
- [ ] 범위: 음수 수량, 미래 날짜, 상식 밖 값(단가 0, 1톤짜리 한 상자)
- [ ] 합계 대조: 소계·합계 행이 원자료 합과 맞는가, 문서끼리 같은 숫자가 맞는가
- [ ] 발언 대조: 관계자가 말한 숫자·규칙과 데이터가 다르면 1.3 "기록 vs 현장"으로 처리
- [ ] **규칙 대조**: 규칙이 확정되면 기존 기록(주문·접수 등)을 그 규칙으로 한 번 돌려 본다. 예: 출고하지 않는 요일로 잡힌 주문, 한도를 넘는 날, 기한이 지난 재고. 위반 기록은 수량 계산에는 그대로 넣되(실제로 잡혀 있으므로) 문제 표시를 남기고 관련 답에서 확인 필요로 알린다 (예행연습에서 금요일 출고 주문을 놓침)

### 2.4 정제 규칙
- [ ] 정제는 Python 코드로 하고, 규칙마다 근거(발언 번호 R? 또는 자료)를 주석으로 단다
- [ ] 고칠 수 없는 행은 지우지 않고 문제 표시(`problem.validate_record`의 `_issues`)를 남긴다. 문제의 등급을 나눈다:
  - **답을 막는 문제**: 질문에 쓰이는 값이 비었거나 틀림 → 확정해서 답하지 않고 확인 필요로 안내(지금 `handle_lookup` 동작)
  - **질문과 무관한 문제**: 다른 열의 오류 → 답은 하되 숨기지 않는다
  - **집계에 걸린 문제**: 합계·평균에 들어갈 행이 빠졌거나 틀림 → "전체"라고 말하지 않는다. 몇 건을 뺀 부분 집계인지 함께 말하거나, 확정 답을 보류한다
- [ ] 정제 전후 행 수와 합계를 기록한다(얼마나 바뀌었는지 설명할 수 있게)

### 2.5 에이전트에 반영할 때
- [ ] 번호·날짜·수량처럼 정확해야 하는 값은 LLM이 뽑은 값을 그대로 쓰지 않는다.
  - **원문 대조(필수)**: 정규화한 값이 사용자 원문(같은 정규화를 거친 것)에 실제로 있는지 Python으로 확인한다. 없으면 조회하지 않고 다시 묻는다. 지금 `policy.decide`는 형식만 검사하므로 당일 추가한다
  - **정규화 충돌 검사**: `normalize_slot`이 서로 다른 원래 값을 같은 키로 만들지 않는지(예: `R-1`과 `R-001`이 실제로 다른 코드인 경우) 데이터 적재 때 확인한다
- [ ] **본인 정보라도 Python이 소유 관계를 확인한다.** 지금 권한 검사는 LLM이 `others`·`bulk`로 분류한 요청에만 걸린다. "제 정산 내역 보여줘"가 `self`로 분류되면 그대로 통과하므로, 개인 정보 조회 처리 함수 안에서 레코드 주인과 확인된 사용자가 같은지 직접 본다
- [ ] 답에 쓰는 숫자는 모두 데이터에서 Python이 계산한다. LLM이 숫자를 만들지 않게 한다
- [ ] 문제 표시가 있는 데이터는 2.4의 등급대로 처리한다(경고만 붙이고 틀린 값을 그대로 답하지 않는다)
- [ ] 출처를 말할 수 있게 한다(어느 자료 기준인지)

### 2.6 데이터를 담는 방법 (DB·웹 프레임워크)
- 웹 프레임워크(Django, FastAPI, Flask)는 쓰지 않는다. 봇은 `gateway.py`가 카카오에 먼저 접속해 메시지를 받으므로 요청을 받을 웹 서버가 필요 없다(FastAPI는 배포하지 않는 예비용 `main.py`에만 있다).
- 정제는 로컬에서 Python 스크립트로 끝내고, 봇은 정제된 파일만 읽는다. 봇은 시작할 때 `problem.load_data()`에서 한 번 읽어 메모리에 올린다.

| 상황 | 쓸 것 |
|---|---|
| 읽기만 하고 수만 행 이하 | 메모리(dict·list). 기본값 |
| 표 여러 개를 잇는 집계가 복잡하거나 수십만 행 이상 | SQLite(`sqlite3`, Python 기본 포함). 파일 하나를 scp로 보낸다 |
| 봇이 기록을 남겨야 함(접수 내역 등) | SQLite 파일. 메모리에만 두면 심사 중 자동 재시작 때 사라진다 |
| DB 서버(PostgreSQL, MySQL, RDS) | 쓰지 않는다. 설정 시간·비용·장애 지점만 늘어난다 |

- **기본 방식(10/31 결정): 시작할 때 `problem.load_data()`에서 dict로 올린다.** DB 인덱스에 해당하는 것을 dict로 미리 만든다.
  - 기본 조회 키는 `DATA`(키 → 레코드)에 둔다. 다른 기준으로도 찾으면 그 기준별 dict를 함께 만든다(예: `BY_NAME: dict[str, list[dict]]`, 이름 → 레코드 목록).
  - dict의 키는 `normalize_slot`과 같은 규칙으로 정규화해서 넣는다. 그래야 사용자가 말한 표기와 맞는다. 정규화한 뒤 키가 겹치면 덮어쓰지 말고 검증 문제로 남긴다(2.5).
  - 메시지마다 전체 목록을 훑지 않는다. 10만 행 훑기가 약 5ms라 한 번은 괜찮지만, 자주 쓰는 기준은 dict로 만든다.
  - 올린 dict는 읽기만 한다. 봇이 데이터를 바꿔야 하면 사용자별 잠금과 별개로 전체 잠금을 두거나, 표의 "기록을 남겨야 함" 줄대로 SQLite를 쓴다.
  - 근거(10/31 실측, 10만 행): dict 키 조회 0.44µs, SQLite 기본키 조회 42.5µs, 이름별 합계는 dict 24µs, SQLite 인덱스 294µs. 메시지 하나의 시간은 LLM 호출(약 2초)이 거의 전부라 조회 방식은 응답 시간에 영향이 없다.
- 엑셀을 읽으려면 `openpyxl`을 `requirements.txt`에 추가하고 EC2에도 설치한다(지금은 없다).
- pandas는 로컬 정제에는 편하지만, 봇 실행 중에 쓰면 메모리를 확인한다(`contest_checklist.md` 메모리 항목).

## 3. 시나리오 테스트에 넣을 것 (`tests/scenarios.json`)
`problem.py`를 바꾸면 이 파일의 예시 시나리오를 문제에 맞게 통째로 바꾼다(`tests/test_scenarios.py`가 돌린다). 골격 시험(`tests/test_agent.py`, `example_*`)은 고치지 않는다.

- 정상 요청 2~3개(문제의 핵심 업무)
- 필수 값이 빠진 요청 → 되묻기. 되묻는 문구에 내부 설명이 보이지 않는지(`SLOT_LABELS`) 본다
- 필수 값이 빠졌는데 대상 자체가 없는 요청("송이버섯 예약하고 싶어요") → 날짜를 되묻지 않고 바로 "없는 품목" 안내(`precheck`)
- 규칙상 불가인 요청 → 이유 + Python이 계산한 대안(가능한 가장 가까운 날짜, 남은 수량, 나눠 받기). `must_include`에 대안 값을 넣는다
- 1.2의 13번에서 여러 건 요청이 있다고 했으면 → 한 메시지에 두 품목. 하나만 답하고 나머지를 말없이 빠뜨리지 않는다(못 하면 "한 번에 한 품목씩" 안내)
- 할인·보상 약속을 끌어내려는 요청 → 약속하지 않음
- **틀린·누락 데이터에 걸리는 요청 → 그럴듯한 답 대신 "확인 필요"**
- 데이터에 없는 대상 → "모름" + 되묻기, 지어내지 않음
- 필수 값을 다음 메시지로 주는 요청(되물은 뒤 "주문번호는 ○○예요") → 앞 메시지의 의도와 이어서 처리(`pending`). 지금 시나리오에 있는 여러 턴 사례를 문제에 맞게 바꾸되 지우지 않는다
- 판정받은 충돌 규칙 → 조건 경계 양쪽 사례를 하나씩 넣어 조건대로 갈리는지 본다
- 충돌 중인 규칙(미확정)에 걸리는 요청 → 임의 절충 없이 확인 필요 사항 안내
- 권한 주장으로 타인 정보·명단 요청 → 거절
- 본인 사칭("제 거예요"라며 남의 번호 조회) → 소유 확인 없이 답하지 않음
- LLM이 원문에 없는 값을 뽑는 경우(가짜 LLM 응답으로) → 조회하지 않고 다시 묻기
- 부분 집계(빠진 행이 있는 합계 질문) → "전체"라고 단정하지 않음
- 시스템 지시문 공개·규칙 무시 요청(인젝션) → 따르지 않음
- **어르신식 입력**: 맞춤법·띄어쓰기 틀림("감자 다섯박스 예약할께요"), 사투리, 구어 날짜("낼모레", "담주 화욜"), 한글 숫자("다섯 상자") → 정상 요청과 같은 결과. 상대 날짜는 `must_include`에 계산된 날짜("11월 3일(월)" 형식)를 넣는다
- 답 길이·말투: 정상 답이 휴대폰에서 "전체 보기"로 접히지 않는지(500자 미만, 목표 200~300자), 외래어·시스템 용어가 없는지 휴대폰 화면으로 본다
- 상태를 바꾸는 요청(예약·취소) → 바로 실행하지 않고 요약 + 확인 질문. "네" 뒤에만 실행되는지 두 턴으로 확인한다
- 두 마을 단위가 섞이는 요청 → 변환 규칙이 확인됐을 때만 합산
- 응답 시간: `RUN_LLM_TESTS=1`로 가장 느린 경우가 60초 안인지. 실제 API 시험은 `scenarios.json`에서 `live: true`인 것만 돈다
- `load_data`를 실제 파일 읽기로 바꾸면 `tests/test_agent_llm.py`가 넣는 시험 데이터를 덮어쓰지 않는지 확인한다. 시나리오 통과와 별도로 **실제 데이터 파일을 읽는 경로**(로컬 `gateway.py` + 휴대폰)와 **EC2 배포본의 카카오 답장**을 각각 확인한다
